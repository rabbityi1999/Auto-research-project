# 科研工作流

定位本技能所在仓库根目录，读取 `docs/protocol.md`。所有代码路径相对于该根目录；实际课题资料保存在 `runs/<topic-slug>/`。不要将用户课题直接作为未经处理的 shell 代码或路径片段。

## 开始或恢复

先找用户指定的已有 run。只有一个相关 run 时用 `python scripts/workflow.py resume <run>` 检查状态、文件校验值和检查点；多个匹配时用课题和时间帮助用户定位。没有 run 时初始化，并将已知需求写入 `brief.md`。用户尚未提供研究主题时询问主题，其余默认中文、近三年加必要经典、组会约 15 分钟，允许用户修改。不要把一次任务变成冗长问卷。

按状态读取一个所需技能，技能目录与本技能同级：

| 状态 | 执行 |
| --- | --- |
| collecting | `../research-survey/SKILL.md` 检索后，用 `../research-briefing/SKILL.md` 向用户介绍 |
| awaiting_selection | 回答用户对候选文献的问题，等待用户明确选文 |
| reading | `../research-reading/SKILL.md` |
| ready_for_slides | `../research-slides/SKILL.md` |
| complete | 给出产物链接；按用户要求继续修改 |

必须在导读后给用户选择机会。推荐列表不等于已选列表。用户可以指定 ID、标题、可明确解析的条件，也可以明确授权 AI 代选；记录真实原话与对应 ID 后调用 `select`。歧义会改变精读范围时，只澄清该歧义。不得因为时间经过、用户沉默或 AI 自己的推荐而继续精读。

选文后自动推进精读、综合和 PPT，无需重复请求已授予的授权。全文缺失只阻塞相关文章；先处理其他所选论文，再向用户说明获取全文或调整选择所需的信息。用户只要求其中一个阶段时，按该范围交付。

## 状态与交付

恢复复制到其他项目的旧工具时，先检查实际脚本路径和 `resume` 返回的工具版本。GitHub 更新不会自动更新副本。读取 `saved_notes_to_review`，优先核验存在但未登记的笔记；不要因 readings 为空就从头再读所有文章。

长任务遵循 `docs/protocol.md` 的“断线与恢复”约定。按查询批次、单篇论文的小节或 PPT 页面批次保存工作文件，再登记 `checkpoint`，不要等整个阶段结束才落盘。检查点记录已完成部分、未完成部分以及下一步可执行动作。不得把聊天进度播报视为磁盘保存，也不声称播报能防止网络断开。

恢复时先确认是否仍有下载、导出或提交进程运行，再决定是否重试。校验通过的精读记录直接复用；有文件但尚未登记的笔记先检查内容，不自动当作完成，也不从头覆盖。若检查点过期，以当前状态和文件为准；等待用户选文的关口始终保留。只能在重新收到执行机会后恢复，不能承诺技能会自行重连客户端。

使用 `scripts/workflow.py` 修改状态；用 `--help` 查看参数。每个阶段保留证据文件。用户改变选择后重新登记已核对的笔记，避免沿用过期状态。依赖工具失败时保存成果、标明尚未完成的步骤；不能用空文件或虚构引用推动状态。

源代码上传授权不包含自动发布调研材料。默认仅保存在 run 内。最终回复给出 PPT 和精读笔记的实际链接，以及影响使用的缺失项。

用户要求自动续跑时读取 `docs/supervision.md`，使用独立监督器；普通运行不自行启动。若 `RESEARCH_WORKFLOW_SUPERVISED=1`，每轮只完成一个可保存单元后返回，让监督器接续，不启动另一个监督器、Codex 或子代理。缺少材料或工具时用 `block` 保存原因。同一 run 不同时由桌面聊天和 CLI 写入。
